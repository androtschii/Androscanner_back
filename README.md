# Androscanner — Backend

Сканер собственной сети с web-панелью, разграничением прав и аналитикой.
FastAPI + PostgreSQL + Celery + nmap/scapy.

Фронтенд: [Androscanner_front](https://github.com/androtschii/Androscanner_front)

---

## ⚠️ Главное правило

**Сканировать разрешено только свои сети.**

Цель проверяется по белому списку CIDR-диапазонов (allowed scope). Проверка
стоит в двух местах:

1. в API — быстрый отказ до постановки задачи в очередь;
2. **внутри самого движка**, перед вызовом nmap — на случай, если движок
   вызовут в обход HTTP: из скрипта, из Celery-задачи, из консоли.

Цель вне списка получает `403`. Все запуски и все отказы пишутся в audit-log.

Побочный, но важный эффект: проверка scope работает и как валидатор ввода.
`ipaddress.ip_network()` не принимает ничего, кроме чистого IP или CIDR,
поэтому подставить свои аргументы в командную строку nmap через поле `target`
нельзя — `-oX /tmp/x`, `192.168.1.1; rm -rf /` и подобное отбиваются
на этом же шаге. Закреплено тестами.

## Возможности

- JWT-авторизация, три роли: **admin**, **analyst**, **viewer**
- Allowed scope: разрешённые диапазоны, настраиваются админом
- 9 профилей сканирования в стиле шаблонов Nessus (nmap)
- Фоновое выполнение через Celery + Redis
- Отслеживание длительности скана (`updated_at`), живой счётчик времени
  на фронтенде пока скан выполняется
- Audit-log всех действий, включая неудачные входы и смену пароля
- Уведомления в Telegram о входах и сканах (опционально, см. ниже)
- Смена собственного пароля — доступна всем ролям
- Отмена скана: админом или тем, кто его запустил
- Аналитика: сводка, сравнение сканов, карта сети
- PDF-отчёты с графиками (WeasyPrint + Pillow)
- CSV-экспорт с длительностью скана
- Миграции схемы через Alembic
- Swagger на `/docs`

## Профили сканирования

9 профилей — по образцу шаблонов сканирования Nessus (Basic Network Scan,
Host Discovery, Advanced Scan и т.д.), адаптированных под то, что умеет
nmap без сторонних движков.

| Профиль | Аргументы nmap | Права | Предел цели | Что делает |
|---|---|:---:|---:|---|
| `ping` | `-sn` | не нужны | 65 536 (/16) | Только живые хосты, без портов — самый быстрый способ узнать, кто в сети |
| `discovery` | `-sn -PR` | **нужны** | 65 536 (/16) | ARP-поиск живых хостов в своём L2-сегменте |
| `quick` | `-sT -T4 --top-ports 100` | не нужны | 4 096 (/20) | TCP connect-скан 100 популярных портов |
| `top1000` | `-sT -T4` | не нужны | 512 | TCP connect-скан 1000 популярных портов |
| `version` | `-sT -sV --top-ports 100` | не нужны | 1 024 | Определение версий сервисов на 100 портах |
| `udp` | `-sU -T4 --top-ports 100` | **нужны** | 64 | UDP: DNS, SNMP, DHCP, NTP — то, что не видно в TCP |
| `vuln` | `-sT -sV --script vuln --top-ports 100` | не нужны | 16 | Известные уязвимости NSE-скриптами (устаревшие версии сервисов) |
| `full` | `-sS -sV -O -T4 -p-` | **нужны** | 256 (/24) | SYN-скан всех 65535 портов + сервисы + ОС |
| `aggressive` | `-sS -A -T4 --top-ports 100` | **нужны** | 64 | Версии + ОС + стандартные скрипты + traceroute разом |

Предел цели разный, потому что стоимость профилей отличается на порядки:
`ping` шлёт по пакету на адрес, `full` — 65535 проб, `vuln`/`udp` ждут
таймаута на каждый порт. Без предела скан `10.0.0.0/8` тяжёлым профилем
принимался бы молча, шёл часами и упёрся бы в лимит времени задачи,
вернувшись как `failed` без объяснения. Теперь отказ приходит сразу и
говорит, что делать.

`quick`/`top1000`/`version`/`vuln` работают без прав не потому, что
«ослаблены» — TCP connect это отдельный тип сканирования, ему raw-сокеты
не нужны в принципе.

Если профилю нужны права, а их нет, скан помечается `failed` с объяснением.
Молчаливой подмены профиля на более слабый **нет**: это скрыло бы от вас,
что скан увидел меньше, чем вы просили.

Пока скан выполняется, фронтенд показывает живой счётчик времени; после
завершения — фактическую длительность (`updated_at - created_at`), как
у Nessus.

## Запуск через Docker (рекомендуется)

Единственный способ, где работает всё сразу: nmap, ARP, Celery, PDF —
и сам сайт, без отдельной установки Node.

Репозиторий фронтенда должен лежать рядом с этим, как соседняя папка:

```
Androscanner/
├── Androscanner_back/    ← этот репозиторий, здесь docker-compose.yml
└── Androscanner_front/
```

```bash
cp .env.example .env
python -c "import secrets; print(secrets.token_hex(32))"   # → JWT_SECRET
# заполни POSTGRES_PASSWORD и DEFAULT_ADMIN_PASSWORD
docker compose up --build
```

Без заполненного `.env` запуск **намеренно падает** с указанием, чего не хватает:
молча подставленный дефолтный ключ подписи опаснее, чем упавший старт.

Поднимутся `db`, `redis`, `api`, `worker` и `web`. Воркер работает в host-сети —
иначе он сидел бы в своей подсети и ARP-discovery не видел бы вашу локалку.
Из-за этого он обращается к Postgres и Redis по `127.0.0.1`, а не по именам
сервисов: в host-режиме внутренний DNS Docker недоступен.

Сайт открывается на **http://127.0.0.1:5173**, API слушает только
`127.0.0.1:8000` — панель управления сканером не должна оказаться доступной
из сети по недосмотру.

Для демонстрации по локальной сети (чтобы зайти с телефона) нужно два
изменения, оба — сознательный компромисс безопасности ради удобства демо:

1. В `.env` этого репозитория: `VITE_API_URL=http://<LAN-IP-этой-машины>:8000`
   — адрес API вшивается в сборку фронтенда, поменять после уже нельзя.
2. В `docker-compose.yml`: у `api` и `web` заменить `127.0.0.1:...` на
   `0.0.0.0:...` в `ports`, и добавить тот же LAN-адрес в `CORS_ORIGINS`.

После любого из этих изменений — пересобрать: `docker compose up --build`.

## Запуск локально на Windows

Работает всё, включая PDF-отчёты — при условии, что поставлен MSYS2 + Pango
(см. «Известные ограничения» ниже) и API запущен через `run-dev.ps1`,
а не напрямую через `uvicorn`.

```powershell
winget install --id Python.Python.3.12 --scope user
winget install --id Insecure.Nmap          # нужен UAC, ставит драйвер Npcap
winget install --id Memurai.MemuraiDeveloper   # Redis-совместимый сервер
```

```bash
cd backend
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
cp .env.example .env
```

В `.env` укажи:

```
DATABASE_URL=sqlite+pysqlite:///./scanner.db
JWT_SECRET=<сгенерируй свой>
NMAP_PATH=C:\Program Files (x86)\Nmap\nmap.exe
```

Три процесса:

```powershell
# 1) Memurai уже работает службой — проверить: redis-cli ping

# 2) воркер Celery
$env:PYTHONIOENCODING="utf-8"
.\.venv\Scripts\python.exe -m celery -A app.tasks.celery_app worker --loglevel=info --pool=solo

# 3) API
$env:USE_CELERY="true"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

`--pool=solo` на Windows обязателен: форк-пул там не работает.

Без Redis тоже можно — при `USE_CELERY=false` сканы выполняются прямо
в процессе API через `BackgroundTasks`. Воркер тогда не нужен.

## Уведомления в Telegram

Опционально — приложение работает и без них. Если задать переменные,
бот присылает сообщения о входах (успешных и неудачных) и о запуске/
завершении сканов.

1. Написать [@BotFather](https://t.me/BotFather) → `/newbot` → следовать
   подсказкам → получить токен вида `123456:ABC-DEF...`.
2. Написать своему новому боту любое сообщение (иначе он не сможет писать
   вам первым).
3. Открыть в браузере `https://api.telegram.org/bot<TOKEN>/getUpdates`
   и найти в ответе `"chat":{"id": ...}` — это `TELEGRAM_CHAT_ID`.
4. Прописать оба значения в `.env`, перезапустить backend (переменные
   окружения читаются только при старте процесса).

```
TELEGRAM_BOT_TOKEN=123456:ABC-DEF...
TELEGRAM_CHAT_ID=123456789
```

Без этих переменных `send_message()` тихо ничего не делает — отсутствие
бота не мешает работе сканера. Сетевые ошибки при отправке (бот
недоступен, нет интернета) тоже проглатываются и только пишутся в лог —
уведомление никогда не должно ронять сам вход или сам скан.

### Команды боту

Бот не только присылает уведомления, но и отвечает на команды —
**только на чтение**, из того же чата, что указан в `TELEGRAM_CHAT_ID`:

| Команда | Что делает |
|---|---|
| `/status` | последние 5 сканов: ID, цель, профиль, статус — с кнопкой «Отчёт» под каждым |
| `/report <id>` | присылает PDF-отчёт по скану файлом в чат |
| `/ip` | текущий IP этой машины в сети — пригождается при смене Wi-Fi/Ethernet |
| `/tictactoe` | крестики-нолики против бота — чем заняться, пока идёт долгий скан |
| `/help` | список команд |

Все зарегистрированы во встроенном меню Telegram (иконка «/» рядом
с полем ввода) — не нужно помнить синтаксис. А под каждым завершённым
сканом в `/status` — кнопка «📄 Отчёт #N»: нажал и получил PDF, не
набирая `/report <id>` руками.

Команды на запуск скана **нет и не будет** — это была бы вторая, не
защищённая RBAC и allowed-scope поверхность для запуска сканов в обход
веб-интерфейса, а у бота нет понятия «роль». Каждый `/report` пишется
в audit-log так же, как скачивание через веб.

Работает через long polling в фоновом потоке, поднимается только когда
заданы `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`. Важно: Telegram не даёт
двум процессам одновременно опрашивать `getUpdates` одним токеном —
если параллельно запущены `pytest` и dev-сервер с одним и тем же
токеном в `.env`, они будут конфликтовать. Поэтому тестовое окружение
(`tests/conftest.py`) всегда явно обнуляет эти переменные.

## Безопасность

Что сделано и почему:

| Мера | Зачем |
|---|---|
| Проверка allowed scope в API **и** в движке | обход HTTP-слоя не даёт сканировать чужие сети |
| `ipaddress.ip_network()` как валидатор цели | закрывает подстановку аргументов в nmap |
| `JWT_SECRET` обязателен, дефолта нет | слабый ключ в проде хуже, чем упавший старт |
| Лимит попыток входа: 5 за 15 минут → `429` | без него пароль перебирается неограниченно |
| Неудачные входы пишутся в audit-log | подбор пароля не должен оставаться незамеченным |
| Журнал только пополняется, ничего не удаляется | иначе подобравший пароль стирал бы следы попыток самим фактом успеха |
| Поля журнала обрезаются валидатором модели | логин из формы входа ничем не ограничен и попадает прямо в `detail` |
| Одинаковый ответ на неверный логин и пароль | иначе по тексту ошибки перебирается список пользователей |
| Минимум 10 символов в пароле | длина даёт больше стойкости, чем обязательный спецсимвол (NIST 800-63B) |
| Предупреждение о слабом пароле админа при старте | `admin/admin` не должен дожить до боевой сети |
| Смена своего пароля (`POST /users/me/password`) | требует текущий пароль: перехваченный токен не даст запереть владельца снаружи |
| Пользователи отключаются, а не удаляются | удаление стёрло бы авторство сканов в журнале; заодно снимает расхождение SQLite/PostgreSQL по внешним ключам |
| CORS ограничен списком, не `*` | |
| `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Cache-Control: no-store`, CSP | Swagger из-под строгого CSP выведен — иначе он не грузится |
| Порты Postgres и Redis только на `127.0.0.1` | |

Чего **нет** и о чём стоит знать:

- **Отзыв токенов.** JWT живёт до истечения срока (по умолчанию 60 минут).
  Частично закрыто: `get_current_user` проверяет `is_active`, поэтому
  токен **отключённого** пользователя перестаёт работать сразу. Отозвать
  токен активного пользователя по-прежнему нельзя.
- **HTTPS.** Не настроен: подразумевается запуск на localhost или за
  обратным прокси. При выносе наружу TLS обязателен.
- **Лимит попыток входа** привязан к логину, а не к IP: распределённый
  перебор по разным логинам им не отсекается.

## Производительность

Замерено на 507 сканах (5.14 МБ JSON в результатах):

| Эндпоинт | Время |
|---|---|
| `GET /scans?limit=20` | 11 мс |
| `GET /health` | 58 мс |
| `GET /analytics/network` | 100 мс |
| `GET /analytics/summary` | 122 мс |

Аналитика разбирает JSON результатов в Python. При таком объёме это
приемлемо; если сканов станут тысячи, потребуется переход на JSONB
и агрегацию в SQL. Замерить перед оптимизацией стоит ещё раз: до замера
казалось, что проблема уже есть, — оказалось, что нет.

`/health` кэширует проверку nmap на минуту: конструктор `PortScanner`
запускает `nmap --version` отдельным процессом, из-за чего проверка
была самым медленным эндпоинтом приложения (277 мс).

## Известные ограничения

- **PDF-отчёты на Windows требуют MSYS2.** WeasyPrint 69 требует Pango ≥ 1.44;
  GTK3-рантайм с gtkd.org несёт 1.42 и не подходит. В Docker Pango стоит
  из коробки. Локально на Windows:
  ```
  pacman -S mingw-w64-x86_64-pango mingw-w64-x86_64-cairo mingw-w64-x86_64-gdk-pixbuf2
  ```
  и `C:\msys64\mingw64\bin` должен быть в `PATH` **до** запуска Python
  (после старта процесса добавлять поздно) — см. `run-dev.ps1`, который
  прописывает это автоматически. Без Pango эндпоинт отдаёт `503`
  с объяснением, а не падает.
- **ARP-discovery требует L2-доступа** к сканируемому сегменту. В Docker это
  обеспечивается `network_mode: host`; в WSL2 нужен
  `networkingMode=mirrored` в `.wslconfig`.
- **Профили `discovery` и `full`** требуют прав администратора (raw-сокеты).
